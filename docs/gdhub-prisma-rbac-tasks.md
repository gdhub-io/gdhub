# Задание для `@gdhub-io/gdhub-prisma`: RBAC

> Пункты 2 и 3 едут одной версией. П. 2 аддитивный, п. 3 удаляет колонку, на
> которой прод ещё работает, — поэтому **ставить эту версию в app можно только
> после прогона бэкфилла на проде** (порядок в конце файла).

## 1. Дополнить enum `AuditAction` — сделано (`2.0.0-beta.41`)

```prisma
enum AuditAction {
  // … существующие значения

  ACCESS_DENIED
  ACCESS_OVERRIDE
}
```

Те же два значения — в TS-union `AuditAction` в `audit/changes.ts`. Логику
аудит-расширения менять не нужно: эти значения пишет только приложение.

Отдельной миграцией, без других изменений: `ALTER TYPE ... ADD VALUE` в ряде
версий Postgres не выполняется в одной транзакции с прочими операциями.

## 2. Добавить `Speciality.isOpenForMentoring`

```prisma
model Speciality {
  // … существующие поля

  /// Человек готов менторить по этой специальности. Отдельно от
  /// `openForQuestions`: выключение менторства не должно стирать выбранные темы.
  isOpenForMentoring Boolean @default(false)
}
```

Миграция должна проставить `true` тем специальностям, у которых
`openForQuestions` непуст, — иначе на деплое все действующие эксперты исчезнут
из витрины:

```sql
UPDATE "Speciality" SET "isOpenForMentoring" = TRUE
WHERE cardinality("openForQuestions") > 0;
```

**Нужно до** того, как приложение переведёт тумблер менторства с `UserRole.Mentor`
на это поле. Вместе с переводом в приложении меняется и витрина экспертов
([api/experts](../src/app/api/experts/route.ts),
[api/expert/[id]](../src/app/api/expert/[id]/route.ts)): фильтр
`openForQuestions: { isEmpty: false }` → `isOpenForMentoring: true`, иначе тумблер
«выключить менторство» ни на что не влияет.

## 3. Удалить `User.roles` и enum `UserRole`

```prisma
model User {
  // убрать: roles UserRole[] @default([Guest])
}

// убрать целиком
enum UserRole { Guest Member Author Mentor Admin }
```

Проверить `extensions/user.ts` — там `deleteAccount` и подсчёты связанных
записей могут трогать `roles`. Из `FIELD_ALLOWLIST.User` тоже убрать `roles`.

**`SpaceMember` в `AUDITED_MODELS` добавлять не надо** — и не только из-за
бэкфилла, который сгенерировал бы строку на каждого пользователя. Смена ролей
из админки уже пишется в `AuditLog` вручную: `logRbacChange` в
[audit.ts](../src/services/access/audit.ts) кладёт строку `space_membership` с
`actorUserId` и `subjectUserId` на каждое изменение. Строка на намерение
(«админ выдал X роль admin») полезнее строки на каждую запись — одно сохранение
в модалке трогает несколько членств.

## Порядок выката

Приложение сейчас читает роль хаба из двух источников сразу: `SpaceMember`, если
строка есть, и legacy `User.roles` через адаптер, если нет. Это и есть окно
безопасности — пока оба живы, порядок можно соблюсти без даунтайма.

| # | Шаг | Где | Почему именно здесь |
|---|---|---|---|
| 0 | `bun run rbac:backfill --dry-run` на прод-базу | прод БД | Read-only. Печатает, сколько людей получат какую роль. Проверяет ту же логику, по которой адаптеры сейчас выдают роли, — **до** того, как ею начнут пользоваться |
| 1 | Задеплоить текущий app с `RBAC_ENFORCE=false` | прод | В нём уже RBAC и мост. Работает и с пустым `SpaceMember`, и с заполненным |
| 2 | Посмотреть `[rbac] would deny` в логах день-другой | прод | Каждая строка — место, где право есть в коде, но не выдано роли |
| 3 | `bun run rbac:seed-matrix` | прод | Заполняет `SpaceRolePermission`. Без него матрица честно репортит `defaults` — работает, но правки из админки лягут на пустую таблицу |
| 4 | Убрать `RBAC_ENFORCE` (дефолт — включено) | прод | Только когда логи чистые |
| 5 | `bun run rbac:backfill` | прод | Переносит пользователей в `SpaceMember`. **Читает `User.roles`, поэтому только пока колонка жива** |
| 6 | `isSuperAdmin = true` одному-двум, SQL | прод | Скриптом не ставится намеренно. Подхватится в течение 5 минут (`USER_SYNC_INTERVAL_MS`) или сразу после релогина |
| 7 | Поставить новую версию пакета | app | Только теперь: в проде уже есть членства |
| 8 | Снять мост + перевести менторство | app | `hub.space.ts`, `roles` из JWT и типов; тумблер и витрина экспертов на `isOpenForMentoring` |
| 9 | Задеплоить app | прод | **До** миграции, не после |
| 10 | Прогнать миграцию (дроп колонки) | прод | Старый код селектит `roles`; если колонка исчезнет раньше нового кода — авторизация ляжет целиком |

**Что shadow-режим не страхует.** `RBAC_ENFORCE=false` отключает проверку
пермишенов, но **не вход в спейс**: `canEnter` смотрит на роль, и если резолвер
роль не нашёл — это 404 даже в shadow. Флаг спасает от «забыли право в матрице»,
не от «адаптер не увидел человека в проекте». Поэтому шаг 0 не пропускать.

**Два способа сломать, оба тихие:**

- **дроп колонки при живом мосте.** `hub.space.ts` делает
  `user.roles?.includes(Admin)` через optional chaining — без колонки это не
  падает, а молча возвращает `Member`. Все админы теряют админку без единой
  ошибки в логах;
- **бэкфилл после дропа.** Восстанавливать членства будет не из чего: кто был
  админом, кто прошёл онбординг — это знала только удалённая колонка.

Откат между 7 и 8 безопасен (просто откатить деплой). После 8 — только из бэкапа,
поэтому шаг 3 обязателен и его отчёт стоит прочитать, а не пролистать.
